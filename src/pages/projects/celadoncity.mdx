## What's implemented

- **CPU** — most of the LR35902 instruction set with interrupt handling,
  dispatched through an opcode table carrying per-instruction cycle counts.
- **MMU** — the full memory map, bank switching, and OAM DMA.
- **Cartridges** — no-MBC, MBC1 and MBC3, including battery-backed save RAM.
- **Video** — background, window and sprite layers rendered per scanline.
- **Audio** — all four channels: two square waves (one with sweep), the wave
  channel and the noise channel, driven by the frame sequencer and mixed to
  44.1 kHz stereo.
- **Timer, serial and joypad.**

## The audio was the hard part

Video is forgiving: draw a frame slightly late and nobody notices. Audio is
not — the APU produces samples at a fixed 44.1 kHz, and if the emulator runs
even slightly fast or slow the buffer starves or overflows and you hear it
immediately as clicks.

The browser build solves this by inverting the usual relationship between the
two clocks. An `AudioWorklet` reports how many stereo pairs it still holds, and
the frame loop nudges its own pace to keep that number near a target of ~4,096
samples (about 93 ms). Video is locked to the audio clock rather than the other
way round, so the picture drifts imperceptibly instead of the sound breaking.

## Running in the browser

The WebAssembly target is built with Emscripten and exposes a flat C ABI —
`gb_run_frame`, `gb_framebuffer`, `gb_set_button`, `gb_save_state` and friends.
The JavaScript side owns only the frame clock, the canvas, the audio graph,
input and persistence; all emulation happens in the wasm module.

Battery saves and save states are written to `localStorage`, keyed per ROM, so
a game you start in the card above survives a refresh.
